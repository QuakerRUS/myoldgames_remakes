# Remakes: Soldier, Piton, Keyboard Simulator — design

Date: 2026-10-22. Author: Fedoseyenko Victor (QuakerRUS).

## Status

All four stages are done (see "Stages" below). This document describes what was built; the
details live in the READMEs of each component and in `docs/formats/`. The analysis of the
originals is in [`docs/originals-review.md`](../originals-review.md).

## Goal

Remake three old projects for Windows and keep them, together with the originals,
in one private repository `QuakerRUS/remakes`.

Guiding principle: **the presentation is far better than the original, while the
functionality and the levels keep their original content.** Every caption and logo that
was drawn with lines (DRAW/CIRCLE) is redrawn as proper graphics.

Sources of the originals (read-only): `E:\Archive\Victor\Work` —
`QBasic\QBasic.zip`, `QBasic\Soldier\{soldier,patch1_1,source1_1}.zip`, `Diplom.zip`.

## Common rules

- Kulakov Taras is removed from the remakes' credits. They read "Program by Fedoseyenko Victor".
- Company: **V Software Entertainment**; place and year: **Russia, Moscow, 2026**. No phone numbers.
- The sources of graphics and sound are not mentioned in the games. All graphics, sounds and
  music are generated by our own scripts in `tools/assets/`; the fonts are SIL OFL 1.1
  (inventory in [`docs/assets.md`](../assets.md)). One consistent style per game.
- UI languages follow the originals: Soldier and Piton in English, Keyboard Simulator in Russian.
- Manual speed tuning (GAME SPEED / REPLAY SPEED loop counts in SOLDIER.CFG, PITON.CFG) is
  replaced by real-time timing.
- The originals in `archive/` are stored byte-for-byte, including Taras's name and demo files.
- All documentation in the repository is in English.

## Technology

- C++20, MSVC 2022 (Visual Studio 2022 generator), CMake ≥ 3.28. Build:
  `cmake --preset vs2022`, `cmake --build --preset release`, `ctest --preset release`
  (`debug` presets likewise). `-DVS_LOGIC_ONLY=ON` builds only the SDL-free logic libraries
  and their tests.
- Dependencies, fetched through FetchContent at pinned versions (`cmake/Dependencies.cmake`;
  archives pinned by SHA-256): SDL3 `release-3.4.18` (window, input, audio device,
  rendering; shared `SDL3.dll`), nlohmann/json v3.12.0, stb at commit `a7d4c21`
  (stb_image / stb_image_write for PNG, stb_truetype for fonts, stb_vorbis for OGG),
  Dear ImGui v1.93.0 (editor and Painter UI), doctest v2.5.3 (unit tests).
- Python 3.12 — only for `tools/import/` (converters) and `tools/assets/` (asset generators).
- Resizable window, logical canvas 1280×720 (letterboxed), fullscreen mode, no filtering
  for pixel art.

### Build output and packaging

Each program is built into its own folder together with its data, so that equally named data
files of different programs do not collide:

| Folder under `build/<preset>/bin/<Config>/` | Contents |
|---|---|
| `Soldier/` | `soldier.exe`, `soldier_editor.exe`, `SDL3.dll`, `data/` (including `data/branding`) |
| `Piton/` | `piton.exe`, `piton_editor.exe`, `SDL3.dll`, `data/` (including `data/branding`) |
| `KeyboardSimulator/` | `keyboard_simulator.exe`, `SDL3.dll`, `data/` |
| `Painter/` | `painter.exe`, `SDL3.dll` |

Test executables (and the engine demo) stay in `bin/<Config>/`. Assets are looked up in
`<exe_dir>/data` first; the source-tree data folder is a development fallback.

`cmake --install build/vs2022 --config Release --prefix dist` produces `dist/Soldier 2.0/`,
`dist/Piton 1.0/` and `dist/Keyboard Simulator 1.0/` (game and version in the name), each
self-contained (with the Visual C++ runtime DLLs) and with a `README.txt`; Painter ships with
Soldier and Piton. `tools/package.ps1` builds Release, installs
and zips each folder into `dist/*.zip`.

Saves and settings: `%APPDATA%\V Software\<game>`.

## Engine (`engine/`)

A small static library shared by all programs (`engine/README.md`). Targets: `vs_engine`,
`vs_imgui` (Dear ImGui with the SDL3 backends), `vs_editor` (tile map editor base). Modules:

| Module | Purpose |
|---|---|
| `app` | window, main loop with a fixed logic step and free-running rendering, scene switching |
| `gfx` | renderer, textures, sprite sheets (JSON), animations (frames + durations), camera, screenshots, window icon |
| `text` | TrueType fonts (stb_truetype), text layout, UTF-8 |
| `audio` | mixer: sound effects (WAV/OGG), looping music, volume |
| `input` | keyboard and mouse, key repeat; no rebinding |
| `ui` | in-game menus, text fields, Yes/No dialogs, buttons |
| `storage` | data and save paths (`%APPDATA%\V Software\<game>`), JSON files (atomic writes) |
| `undo` | undo/redo stack |
| `editor` (`vs_editor`) | common base of the map editors: field grid, palette, frame cursor, undo/redo, file dialogs, Save? prompt, test-play |

Game logic is separate from rendering: the level model and the rules are plain C++
without SDL (`soldier/core`, `piton/core`, `keyboard-simulator/core`) and are covered by unit
tests (doctest).

## Soldier 2.0

### Content (unchanged from 1.1)

- The 51 levels of patch 1.1. A time limit remains only on levels 1, 24, 33 and 34
  (300, 120, 36 and 15 timer units, see below); the other levels have none.
- The field is a grid of tiles; each level has its own size (up to 100×100).
- The rules are an exact port of `GAME1.BAS` version 1.1 (`soldier/core/README.md`):

| Code | Tile | Behaviour |
|---|---|---|
| 0 | floor | walkable |
| 1 | wall | blocks |
| 2 | exit | stepping on it wins the level |
| 3–6 | player on floor (down/up/left/right) | level start |
| 8 | box | can be pushed if the cell behind it is floor, a button, an open door, water or a sunk box |
| 9 | button | pressed while the player, a box or a key is on it |
| 10 | box on button | |
| 11–14 | player on button | |
| 15 | door | open only while every button of the level is pressed |
| 16–19 | player in door | |
| 20 | box in door | |
| 21–44 | 6 coloured keys and doors: per colour a key, a door, a key on a button, a key in a door | a key goes to the inventory (up to 25); a coloured door opens with a key of its colour when entered; Space/Enter puts the selected key in front of the player or opens the door in front |
| 45 | dark wall | turns into a plain wall when the player tries to pass |
| 46 | fake wall (looks like a dark wall) | walkable |
| 48 | guillotine | closed during the 4th quarter of every second; cannot be entered while closed; a player inside when it closes dies |
| 49–52 | player under guillotine | |
| 54 | water | stepping into it kills; a box pushed into water sinks and becomes a sunk box |
| 56 | sunk box | walkable |
| 57–60 | player on sunk box | |
| 63 | box on sunk box | |
| 7, 47, 53, 55, 61, 62 | death tiles | gave up (Esc), time out, guillotine, drowned, gave up / time out on a sunk box |

- Controls as in the original: arrows step/push/turn (holding an arrow keeps walking),
  `,` `<` and `.` `>` turn counter-clockwise and clockwise, Tab selects the next inventory
  item, Space/Enter uses the item, Esc gives up. Added: P pauses, Z toggles the zoom.
- The rhythm is kept in ticks: a game "second" is 4 ticks, a step takes 2 ticks, the
  guillotine is closed on the 4th tick of the "second", the level timer decreases once
  every 4 ticks. This is needed for the timing puzzles and for replaying the old demos.
- The default pace is the original's "real second": tick 250 ms, step 0.5 s.
  The timer shows the original numbers (300, 120, 36, 15) and, as in the original,
  decreases by one every 4 ticks — at ×1 that is 1 real second.
- Game speed is the GAME SPEED setting in OPTIONS: 5 steps ×0.5, ×0.75, **×1 (default,
  tick 250 ms)**, ×1.5, ×2 (tick 500 … 125 ms). Only the tick length changes; all logic and
  the timer run in ticks, so the timer numbers do not depend on the speed (×1 is the original pace),
  and neither do the recordings.
- Bugs of the original are fixed (none of them affects the 51 LISIY demos):
  - pushing a box to the right checked the wrong cell for a sunk box (`ml(absx - 2, absy)`
    in subroutines 2300 and 5600);
  - Tab (next inventory item) was unreachable in 1.1;
  - using an item while under a guillotine or on a sunk box used a stale target cell;
  - a bump while standing on a sunk box did not turn the player;
  - the "hang the computer" routine on tampered saves is removed (saves are plain JSON;
    progress is verified against the records instead, see "Menu and saves");
  - the turn keys and Space were not recorded by the 1.1 recorder; now every command is
    recorded;
  - outside the map is treated as wall — a guard against leaving the array (the original
    continued the level with floor cells and crashed at index −1/101); on the shipped levels
    only levels 25 and 28 have a reachable edge pocket, behind boxes; in normal play nobody
    goes there.

### Presentation

- Tiles are 32×32 world pixels. The map is drawn at **2× by default (64 px cells)**; Z
  (in the game and in a replay) or OPTIONS → ZOOM toggles between 2× and 1× (32 px cells);
  the choice is saved. The camera shows as much of the field as fits and smoothly follows
  the player.
- Animations: walking and turning, pushing a box, a button pressing in, a door opening,
  picking up a key, the guillotine going down and up, flowing water, a box sinking,
  each kind of death.
- A sound for every action, music in the menu and in the game, faster music while the
  timer is at 15 units or less.
- Side panel: level, timer (green > 59, yellow 15–59, red < 15), 5×5 inventory with a
  cursor, a key help. The HEALTH/ARMOR/AMMO lines of the original (always 100/0/0) are dropped.
- Intro: animated logo "V Software Entertainment presents", then "SOLDIER",
  "Program by Fedoseyenko Victor", "Russia, Moscow, 2026", version 2.0. Any key skips.

### Menu and saves

- 10 player slots with a name (up to 8 characters, A–Z, 0–9) and the level reached.
  Tab or the arrows select a player.
- Items: NEW GAME (enter a level not above the one reached), REPLAY LEVEL (show the best
  run of a completed level), DELETE PLAYER (with confirmation), OPTIONS (game speed,
  sound and music volume, zoom, fullscreen), EXIT.
- Saves are JSON (`save.json` and `records/slot<N>/<LL>.json`). Progress is protected by the
  records instead of the original's "hang the computer" routine: on load, a player's level
  reached is 1 + the largest k such that his records 01..k all exist, name him as `player` and
  replay (on the shipped levels) to a win at their recorded end tick. A higher (or lower)
  `level_reached` in `save.json` is replaced by that value, logged and written back; no message
  box. Every win writes a record, so honest play is unaffected; LISIY is verified with his
  shipped records (see `soldier/core/README.md`, "Progress proven by records").
- A run is recorded as a list of (tick, command); on a win it becomes this player's record
  for the level if there is none yet or it is shorter. Replay: speed ×1/×2/×4 (keys 1, 2, 4,
  Tab cycles), Z zoom, any other key exits.
- The built-in player LISIY (all 51 levels completed) with his `REC0*.DAT` records
  (converted from the old format). Taras's demos and save are not carried over. The release
  package leaves LISIY out (no `players.json`, no `records/`): a new install starts with no
  players; the repository and development builds keep him for `--verify-replays`.
  After level 51 — "YOU WIN!".

### Data import

`tools/import/` converts:
- `LEVELn.DAT` (header: 4 × int16 — width, height, time, number; then width×height
  bytes of codes, row by row) → `soldier/data/levels/NN.json`
  ([format](../formats/soldier-level.md));
- `REC0nn.DAT` (int32 seed, int32 speed, then triples of int32 part number, int32 iteration
  inside the part, 4 bytes of `INKEY$`) → recordings in the new format
  ([format](../formats/soldier-recording.md)); each one is verified by running the original
  1.1 replay logic until the exit.

The new graphics are drawn by `tools/assets/gen_soldier_gfx.py` after the original sprite set.

### Soldier map editor

`soldier_editor.exe` (`soldier/editor/README.md`), modelled on the EDITOR of Soldier 2.0:
- the field grid on the left, the object palette on the right (grouped tiles, drawn with the
  game sprites); Tab switches the panel, the arrows move the frame cursor, Space/Enter places,
  Backspace resets to floor; mouse: LMB places, RMB erases, wheel zooms, middle button pans;
- level number, size, time limit (0 = none);
- undo/redo, new/open/save/save as, Esc asks "Save the level?" Yes/No/Cancel;
- level check: errors (no player start, no exit) block test-play; warnings for extra player
  tiles, an exit not reachable, doors without buttons, coloured doors without keys;
- test-play the level in the game with one key (F5).

## Piton

### Game

- A 38×23 field, a snake of 3 segments, arrows set the direction (up to 2 turns are queued),
  a 180° turn is not allowed; hitting the border, a brick or itself is GAME OVER.
- A rabbit appears on a random free cell; eating it makes the snake longer.
- 10 levels with brick walls, growing in difficulty (`piton/data/levels/NN.json`,
  [format](../formats/piton-level.md)): 01 Open Field, 02 Four Pillars, 03 Twin Walls,
  04 Cross, 05 Fortress, 06 Comb, 07 Four Rooms, 08 Spiral, 09 Catacombs, 10 Labyrinth.
  **Each level requires eating 50 rabbits**, then the next level starts. After the 10th —
  a victory screen.
- One speed, real-time: 8 ticks per second (125 ms per cell), with smooth movement between
  ticks. "READY" / "GO!" before each level; P pauses (also on losing window focus).
- Score: 10 × level per rabbit, 500 × level for completing a level; the high score is kept.
- Menu: NEW GAME (select any unlocked level), DEMO, OPTIONS (sound, music, fullscreen), EXIT.
  In DEMO the computer drives the snake (shortest path to the rabbit that keeps its tail
  reachable, otherwise it follows its tail); levels go in order and repeat; any key returns
  to the menu.
- Only the level reached, the high score and the settings are saved (`piton.json`).
- The progress is protected against hand-editing (a deterrent, not real security): `piton.json`
  holds `"sig"`, the lower-case hex HMAC-SHA256 of the canonical text
  `piton-save/1
level_reached=<n>
high_score=<n>
` under a key compiled into `piton.exe`
  (stored XOR-masked; SHA-256/HMAC are implemented in `piton/game/src/hmac_sha256.*`, no
  extra dependency, checked against the RFC 4231 test vectors). On load, a missing or wrong
  `sig`, progress fields that are not integers, or an unreadable file reset the level reached
  to 1 and the high score to 0; the settings (volumes, fullscreen) are kept, a correctly
  signed file is written at once, and the menu shows "SAVE FILE WAS MODIFIED - PROGRESS
  RESET" once. A file without progress fields and without `sig` (settings only) is accepted.
  Loading never crashes on odd contents.

### Presentation

- An animated snake: the head in several phases per direction, body, turns, tail — after
  the original sprite set, at the new resolution. As the original's many sprites intended,
  every segment shows the crawl: the skin markings move through each body and turn cell
  together with the head and tail. An animated rabbit. New grass and
  brick textures.
- Sounds (eating, turning, death, level complete, menu), music (menu, game, victory).
- The same company intro, then "PITON".

### Piton map editor

`piton_editor.exe` (`piton/editor/README.md`), on the shared `engine/editor` base: a 38×23
field; objects are brick, empty, and the snake's start position and direction. Same keys,
mouse, undo/redo and F5 test-play as the Soldier editor, plus symmetry painting
(horizontal / vertical / both), tools (clear field, fill border, flip, mirror half), and a
live level check (`piton::checkLevel`: free start, 6 free cells ahead, one connected region,
enough free cells, no long dead ends).

## Painter (graphics editor)

`painter.exe` (`tools/painter/README.md`), shared by Soldier and Piton, in the spirit of
PAINTER2:
- opens and saves PNG images and sprite sheets (a PNG plus the engine's sprite-sheet JSON
  next to it);
- tools: pencil, eraser (transparent), fill, line, rectangle, filled rectangle, colour picker,
  select (move, copy/cut/paste, flip), frame rectangle and pivot for sheets;
- frames and animations panels (per-frame durations, loop flag), animation preview, onion skin;
- palettes: built from the image, or loaded/saved as `.hex` and `.gpl`;
- undo/redo of every edit;
- keyboard mode like PAINTER2: a frame cursor on the pixel grid, Tab to the palette,
  Space/Enter paints, so the keyboard alone is enough to draw.

## Keyboard Simulator

A remake of the 2007 thesis program "Клавиатурный симулятор слепой печати"
(touch-typing simulator); `keyboard-simulator/core/README.md`, `keyboard-simulator/app/README.md`.

- One window in a modern design with the layout from the thesis:
  - the text field on top: the current and the next sentence, word wrap, the current
    letter marked by a cursor;
  - a stats line: speed (characters per minute), errors, accuracy, time;
  - buttons: Рестарт, Пауза, Помощь, О программе (Restart, Pause, Help, About), with
    hotkeys F2, F3, F1, F4; a sound switch (F5);
  - an on-screen ЙЦУКЕН keyboard below, keys coloured by finger, with the finger legend
    "5 4 3 2 1 / 1 2 3 4 5"; the key to press is highlighted, and for capitals and
    shifted symbols the Shift of the opposite hand is highlighted too.
- Behaviour as in the thesis: a correct key moves the cursor; a wrong key counts as an
  error and briefly flashes; a space is required at the end of a line; after `.`, `!`,
  `?` the sentence leaves, the next one moves up, and a new random one is added below.
- Input by the actual Russian character (SDL text input), not an emulation on top of QWERTY;
  a Latin letter shows a hint to switch the keyboard layout.
- Speed is measured in real time with millisecond precision; Pause stops the clock,
  Restart resets the stats.
- Texts: the same 5630 sentences from `text_rus.txt`, converted from CP866 to UTF-8
  ([format](../formats/kbsim-texts.md); the last line of the original has no line break,
  so counting line breaks gives 5629).
- Bugs of the original are fixed: the capital "Е" could not be typed, the digits were
  shifted by one (a "1" in the text was shown and expected as "2", "9" as "0"), and "0" was
  impossible to type (see [originals-review.md](../originals-review.md)). Every character is
  now matched exactly.
- No user profiles, lessons or statistics history.
- About: Keyboard Simulator, Program by Fedoseyenko Victor,
  V Software Entertainment, Russia, Moscow, 2026.

## Verification

- Unit tests of the logic: Soldier's rules for every tile, every LISIY demo replayed to
  the exit, Piton's rules (growth, collisions, rabbits only on free cells), the level checks
  and the demo AI on every level, speed and error counting in Keyboard Simulator, every
  character of the texts typeable.
- Every Piton level is checked by `piton::checkLevel` (all free cells in one region, among
  other rules).
- The editors and Painter have `--roundtrip` checks (load + save of every shipped file is
  byte- or pixel-identical) and `--smoke` / `--screenshot` runs without a visible window.
- A manual check of every program before a stage is handed over.
